# Архитектура FluxGate

## Назначение

FluxGate — самостоятельная панель аренды и управления SNI-прокси. На одном VPS работают HAProxy с quota watchdog и панель с тремя процессами одного Go-бинарника: supervisor, web и traffic agent. Администратор добавляет конечные HTTP или HTTPS серверы по IP и порту, назначает точный SNI или wildcard третьего уровня, управляет доступом, квотами, скоростью, мониторингом, арендой и Telegram-уведомлениями.

## Путь пользовательского трафика

`settings.proxy_mode` выбирает `relay` (по умолчанию для старых и новых баз) или `direct`. API сохраняет режим вместе с остальными настройками транзакционно; при ошибке валидации/SQL восстанавливает прежние in-memory настройки и конфиг. `PUT /settings` без `proxy_mode` сохраняет прежний режим. Далее сначала описан relay.

```text
Клиент TLS/HTTP/WS → :443 HAProxy public_sni (TCP, читает SNI)
  → relay_<id> PANEL_DATA/relay-<id>.sock (Unix, Go: квота, скорость, счётчики)
  → HAProxy internal_tls 127.0.0.1:8443–8458 (least-active TCP shard, TLS terminate, HTTP)
  → target_<id> IP:port (HTTP/HTTPS, WS upgrade)
```

Основной домен и незнакомый SNI идут через `relay_fallback` (`PANEL_DATA/relay-0.sock`) к `internal_tls`, затем к `fallback_page` 127.0.0.1:8181. Relay-сокеты имеют 0600, принадлежат агенту и удаляются при закрытии listeners. Повторный агент защищён flock; активный socket и посторонний файл не заменяются. Внутренние порты доступны только локально. `public_sni` принимает все интерфейсы на 443. Панель отдельно слушает 9389 и не проходит через HAProxy.

`config.go` строит ACL, размещая точные имена перед wildcard. В fallback входит главный домен; значение можно менять в настройках. Конфиг сначала пишется во временный файл, проверяется `haproxy -c`, затем атомарно заменяет `haproxy.cfg`. Watcher замечает изменение и плавно перезапускает HAProxy. Go создаёт self-signed ECDSA P-256 сертификат на каждый SNI с расшифровкой и fallback; клиентам требуется доверять ему самостоятельно. TLS-проверка upstream опциональна.

### TLS passthrough на отдельном маршруте

`routes.tls_passthrough` (`false` по умолчанию) независим от глобального режима. Идемпотентная additive-миграция добавляет INTEGER NOT NULL DEFAULT 0; старая база/backup сохраняет расшифровку. POST принимает bool, PUT без поля сохраняет прежнее значение. Backup переносит настройку и валидирует сочетание `tls=true`, `verify=false`: TLS peer — клиент, не FluxGate. Панель не создаёт и не загружает сертификат для нового passthrough-маршрута.

| Режим | Путь маршрута | Учёт / ограничения |
| --- | --- | --- |
| relay, расшифровка | public_sni → Go → internal_tls → upstream | TLS-байты, строгие квоты Go |
| relay, passthrough | public_sni → Go → TLS upstream | TLS-байты, те же строгие квоты Go |
| direct, расшифровка | public_direct TLS → upstream; при mixed: public_direct TCP → tls_bridge → internal_tls → upstream | HTTP/WS-байты, opt-in мягкие квоты/HAProxy bwlim |
| direct, passthrough | public_direct TCP → TLS upstream | TLS-байты, opt-in мягкие квоты/HAProxy bwlim |

При наличии хотя бы одного passthrough в direct генерируется TCP `public_direct` с ClientHello inspection 5s. ACL основного домена первый; далее **все** маршруты в общем порядке exact/wildcard, в том числе обычные. Иначе wildcard passthrough перехватил бы точный обычный SNI. Обычный/fallback трафик идёт в `tls_bridge` с leastconn по 16 loopback TCP-входам 8443–8458, затем в `internal_tls`. Это не Go relay. Внешний maxconn N, внутренний N+reserve, глобальный 2N+reserve. Readiness проверяет внутренние listeners. Без passthrough сохраняется прежний одношаговый direct с global N+reserve.

Opaque backend имеет прежнее имя `direct_<id>_<meterID>`, `mode tcp`, `server target IP:port` **без ssl**, `tcp-request content set-bandwidth-limit`; contstats и checkpoint-учёт всех workers сохраняются. `tls_bridge` не попадает в direct collector, поэтому двойного счёта нет. Quota/watchdog/pause используют тот же Runtime API, включая draining workers. Новое соединение при блокировке закрывается без 429/503, поскольку ответ потребовал бы расшифровки. Relay также не вызывает TLS.Server при отказе passthrough, а dial идёт прямо к реальному IPv4/IPv6 upstream. Проверка состояния после dial не допускает подключения со сменившимися IP/портом/режимом. При смене галочки активные relay-соединения маршрута закрываются; direct без bandwidth limit может завершить уже открытые сессии в прежнем режиме до их закрытия/hard-stop. Счётчики не сбрасываются.

Ни Go, ни HAProxy не расшифровывают passthrough и не меняют SNI/ALPN/HTTP-заголовки/путь. Сертификат и TLS-совместимость обеспечивает upstream, его проверяет клиент. Поддерживаются TLS-протоколы поверх TCP, в том числе HTTP/2/WS при поддержке upstream; UDP/QUIC отсутствует. Для маршрутизации нужен видимый ClientHello SNI; скрытый ECH SNI маршрутизировать нельзя. Исходный IP клиента не передаётся (PROXY protocol не добавляется). HTTP-метрики TCP backend не собираются, API `/request-stats` возвращает `http_visible=false`, UI показывает недоступность, а прежняя HTTP-история остаётся. Миграция не меняет сетевые параметры VPS и не устраняет аппаратные/драйверные сбои.

Основание: [HAProxy TCP proxy](https://www.haproxy.com/documentation/haproxy-configuration-tutorials/protocol-support/tcp/) и [HAProxy 3.2 bandwidth filters](https://docs.haproxy.org/3.2/configuration.html#9.7). Functional integration проверяет сертификат upstream, смешанные exact/wildcard, active WS accounting/reload, квоты/паузы/topup, общую скорость и backup/restore, включая reserved capacity двух frontend, без 100k-нагрузки.

### Счётчики, квоты и скорость

#### Прямой режим

В `direct` **без passthrough-маршрутов** работает единственный `public_direct` HTTP frontend с TLS на `:443`: `клиент → HAProxy → direct_<id>_<meterID> → upstream`. Сертификаты и ACL `ssl_fc_sni` те же; основной и неизвестный домены идут к `fallback_page :8181`. Внутренний TLS frontend и relay backend отсутствуют. Неиспользуемые Go Unix listeners остаются для обратного переключения; данные через них не идут. Глобальный HAProxy maxconn равен N+reserve вместо 2N+reserve. HTTP/WebSocket и upstream TLS verification сохраняются.

`settings.direct_limits` — отдельный opt-in, по умолчанию false, включая старые direct-установки. Без него квоты/скорость не применяются, UI предупреждает и отключает соответствующие поля. При true HAProxy использует bwlim-in/out и одну integer stick-table запись на backend для общей скорости всех потоков маршрута. Дневная/месячная квота **мягкая**: collector после снимка переводит backend в maintenance и выполняет shutdown sessions server на всех известных workers, затем возвращает ready после пополнения/смены периода. Статус — quota, уведомления включены. Новые запросы с расшифровкой получают 503; passthrough закрывает TCP. При reload старые потоки с bandwidth limit закрываются, чтобы бюджеты разных workers не суммировались бесконечно; короткое перекрытие до опроса возможно. Остальные туннели сохраняют graceful reload. Пауза, удаление и смена режима также закрывают прежние соединения. Строгая граница байтов остаётся только в relay.

`direct.go` опрашивает `bin`/`bout` backend через Runtime API каждую секунду. `option contstats` обновляет незакрытые потоки примерно раз в 5 секунд; скорость — средняя за 10 секунд. При расшифровке это HTTP/WS-байты без TLS/TCP/IP; у passthrough backend — зашифрованные TLS-байты без TCP/IP. История двух режимов не пересчитывается задним числом и не идентична счётчику всего порта/провайдера. См. [HAProxy contstats](https://docs.haproxy.org/3.2/configuration.html#4-option%20contstats).

У softly stopped backend HAProxy может отвергать server-команды с `Proxy is disabled.`, хотя upgraded streams ещё работают. Тогда отключение использует короткий `show sess backend <name>` и `shutdown session <id>` только для проверенных идентификаторов этого backend, пакетами до 64 CLI-команд. Master-target повторяется для каждой команды пакета. Список ограничен 128 MiB (не выделяется заранее), адреса/содержимое не пишутся в лог. Reader считывает chunks вместо обработки ответа по одному байту. Неизвестный ответ считается ошибкой, а не подтверждением; исчезновение одной генерации не мешает watchdog попытаться закрыть остальные. Таймаут чтения в интеграционном тесте не считается успешным отключением туннеля.

Worker определяется по node, Start_time_sec и PID (нужен HAProxy 3.2). Независимый 128-битный `route_meter_ids.token` не позволяет при повторном использовании SQLite route ID присвоить старый трафик новому серверу. Панель держит интерактивный stats connection к каждому обнаруженному worker; этот connection удерживает softly stopped worker до нуля клиентских соединений и сохранения финальных счётчиков. Watcher перед reload ждёт `haproxy.reload-ready` на новый nonce из `haproxy.reload-request`. Если панель не отвечает, старый конфиг продолжает работать, reload повторяется позже. Ручной reload в обход watcher не даёт этой гарантии.

Дельты добавляются в память маршрутов; `direct_checkpoints` и totals/periods/samples фиксируются **одной** транзакцией в `accounting.go`. Ошибка commit не продвигает долговечный checkpoint; после рестарта панели счётчик продолжается, а не берётся заново целиком. Неактивные checkpoints удаляются через 48 часов. После рестарта только панели старые живые workers дополнительно опрашиваются через master CLI; возможна потеря хвоста worker, завершившегося до следующего опроса. Crash/hard-stop HAProxy может потерять ещё не снятые байты, а отказ диска расширяет окно потери. Это не журнал финансового биллинга с гарантией нулевой потери при аварии.

`RouteState.mu` не удерживается во время Runtime API/SQL. Collector использует короткий `direct.dataMu` вместо `stateMu`. Writer под этим mutex снимает вместе checkpoints и соответствующие route totals, отпускает его до SQL, после commit удаляет только совпадающие сохранённые checkpoints и вычитает только сохранённые дельты. Новые наблюдения во время SQL остаются pending. Draining worker закрывается после подтверждения независимого writer; collector сам не вызывает flush. Маршрут, временно исключённый из конфига для удаления, остаётся доступен учёту до commit/rollback. Stats connections принадлежат одному фиксированному worker; ошибки ограничены по времени и логируются не чаще раза в минуту. `/system` показывает время последнего успешного чтения и ошибки; UI предупреждает о задержке статистики.

#### Режим relay

Go relay считает байты TLS-потока (включая TLS-заголовки, без TCP/IP). Для маршрута выбирается учитываемое направление: `up` (приём), `down` (отдача), `both`. Дневная квота сбрасывается в 00:00 `PANEL_TIMEZONE`. Месячная начинается в день создания маршрута, при отсутствии числа используется последний день месяца. Пополнение `topup` увеличивает только текущий период. После лимита текущие соединения закрываются, следующие запросы с расшифровкой получают 429. Пауза даёт 503. В passthrough вместо HTTP-ответа закрывается TCP. Общая скорость маршрута ограничивается token bucket по направлениям.

`relay.go` передаёт блоки через переиспользуемые буферы 16 KiB (32 KiB на двухсторонний туннель). Ошибки закрывают обе стороны и отменяют ожидание limiter. Для TLS-потока EOF со стороны внешнего frontend включает 30-секундный idle-drain ответа: обновление read/write deadlines синхронизировано, активный ответ не имеет общего 30-секундного лимита. Go не посылает преждевременный TCP FIN во внутренний TLS frontend, который мог оставить upgraded upstream занятым до часа. При истечении idle-drain внутреннее соединение сбрасывается RST. После завершения обеих передач внутренняя сторона также закрывается с linger=0, внешняя — обычно, без отбрасывания переданного ответа. Для обычных TCP-потоков сохранён half-close. Неактивные чтения/записи незавершённых туннелей ограничены 1 часом. Квота резервируется до записи, а учитываются фактически записанные байты. Незавершённые записи при смене дня/месяца относятся к исходному периоду. Новые заблокированные соединения с расшифровкой получают ограниченный по времени TLS/HTTP-ответ 429/503 от relay, без ожидания reload HAProxy. Passthrough закрывается без TLS handshake со стороны Go.

Путь проходит через два frontend одного HAProxy. `PANEL_MAX_CONNECTIONS` задаёт внешний лимит N (по умолчанию 10000); внутренний лимит — N+reserve, общий — 2N+reserve, reserve=max(8,min(256,N/10)). Внешние pending handshakes не могут занять все места внутреннего входа. После лимита новые клиенты ожидают в системной очереди; это ограничение одновременно открытых соединений, не Мбит/с. ClientHello должен поступить за 5 секунд, иначе `WAIT_END` отклоняет поток. Внутренний TLS/HTTP клиент имеет idle timeout 30 секунд, WebSocket tunnel — 1 час.

Диапазон N — 1–100000 в обоих режимах. При 100k relay: внешний 100000, внутренний 100256, общий 200256; direct без passthrough: внешний 100000, общий 100256; смешанный direct: внешний 100000, внутренний 100256, общий 200256. Эти лимиты относятся к текущему HAProxy worker, старые поколения дополнительно дренируют соединения. Агент применяет общий atomic admission cap N **до** создания goroutine/dial/буферов — для всех маршрутов, fallback и поколений вместе. При переполнении закрываются только новые подключения, действующие не вытесняются; число отказов доступно в диагностике. В неё входят и подключения в setup/reject, а не только установленные route tunnels.

Оба локальных TCP перехода раньше имели конечный пул ephemeral ports. Вход HAProxy→Go переведён на Unix. Обратный Go→HAProxy сохраняет TCP для abortive close RST: полностью Unix-вариант воспроизводимо оставлял внутренний upgraded stream после закрытия клиента. `internalTLSIngress` выбирает минимальную активную загрузку из 16 портов 8443–8458, равные — по кругу. Место резервируется под коротким mutex и освобождается после закрытия или ошибки dial; сетевые операции не удерживают mutex. Это 16 разных TCP destination tuples с запасом по портам, а не просто увеличение maxconn. Healthcheck проверяет все 16 listeners. Внешние upstream TCP pools этим не расширяются: одно исходящее IP→IP:port соединение требует отдельного исходящего порта. Docker задаёт `ip_local_port_range=10000 65535` в своём namespace, хост не меняется. Для 100k длительных соединений к одному сервису нужны несколько настоящих upstream endpoints/исходящих IP и соответствующая маршрутизация/NAT, не несколько SNI к одному endpoint.

Docker и systemd разрешают 1048576 FD на процесс; HAProxy сам рассчитывает нужный soft limit из maxconn. При N=100k только HAProxy relay может держать около 400k сокетов, Go — около 200k, без старых workers/прочих FD. Relay-буферы при 100k требуют ~3,05 GiB отдельно от TLS, goroutines, kernel sockets и upstream. Нельзя считать поддержку настройки доказательством вместимости конкретного хоста. Диагностика FD кэшируется 30 секунд и читает каталог небольшими страницами без сортировки; heap берётся через runtime/metrics без ReadMemStats на каждом UI poll.

`accounting.go` раз в `PANEL_FLUSH_INTERVAL` (по умолчанию 5 секунд) сохраняет изменившиеся `routes`, `periods` и дельты `samples` одной транзакцией для всех маршрутов. Во время SQL блокировки relay не удерживаются. Буфер дельт уменьшается только после успешного commit; ошибка БД приводит к повтору без потерь и удвоения. Скорость рассчитывается независимым секундным worker по реальному интервалу. SIGTERM/SIGINT закрывают listeners и соединения, дожидаются goroutines и сохраняют остаток перед закрытием SQLite. Backup также начинается с сохранения остатка. При аварии теряются данные после последнего успешного commit. UI запрашивает `historyAPI` и агрегирует до 60 точек.

HTTP-метрики сохраняются общей транзакцией раз в 10 секунд; baseline продвигается только после успешного commit. Индексы `samples(ts)` и `request_samples(ts)` ускоряют общую историю и очистку. Writer использует WAL и `SetMaxOpenConns(1)`; web читает историю/CSV через отдельный read-only пул до 4 соединений. Контрольные изменения и сохранение сериализованы через `stateMu`; `RouteState.mu` защищает короткие операции в памяти. Медленная БД может задержать API/историю, но не должна блокировать передачу данных.

`history.go` кэширует только готовые агрегированные графики на 30 секунд (до 64 ключей), объединяя одновременные одинаковые запросы через отменяемую очередь. Запрос/ожидание ограничены 10 секундами и контекстом HTTP-клиента. Создание/удаление маршрута меняет epoch кэша, чтобы переиспользование ID не выдавало прежнюю историю. Retention остался 90 дней: раз в минуту удаляются пакеты до 5000 строк, максимум 8 пакетов на таблицу за запуск с общим бюджетом 2 секунды; backlog продолжается в следующий запуск. Текущие totals, квоты и платежи не затрагиваются.

HAProxy конфигурация строится из снимков маршрутов под mutex, с детерминированной сортировкой и ID как последним критерием. Идентичный файл не переписывается. Watcher запускает один master-worker и отправляет master SIGUSR2 для reload, передаёт TERM/INT и сообщает об неожиданном завершении master. Старые workers завершаются после закрытия соединений; `hard-stop-after 1h` ограничивает draining. Соединения на старом worker через час после reload будут закрыты. См. [HAProxy management guide](https://docs.haproxy.org/3.2/management.html).

### HTTP-запросы

`requeststats.go` каждые 10 секунд читает HAProxy Runtime API `show stat` из Unix socket. Для backend `target_<id>` (relay) или `direct_<id>_<meterID>` берутся `req_tot`, ответы 2xx/3xx/4xx/5xx, активные соединения и среднее время ответа. Дельты записываются в `request_samples` и `request_totals`; первый снимок служит baseline, так как HAProxy уже мог обслуживать трафик до запуска панели. После reload HAProxy уменьшение счётчика трактуется как сброс. Эти HTTP-метрики опрашивают только текущий worker, в отличие от direct-учёта байтов всех workers; для строгого подсчёта запросов через reload они не предназначены. График показывает историю с момента включения сбора, не восстанавливает прошлые запросы из TLS-байтов. Счётчик активных соединений может включать длительные WebSocket-сеансы.

### Мониторинг и уведомления

TCP проверка IP:port выполняется примерно раз в 10 секунд; опциональное Telegram-уведомление отправляется через 5 минут непрерывной недоступности, затем при восстановлении. Это проверка доступности порта, не HTTP-ответа. Telegram API может указывать на HTTPS-зеркало. Bot token хранится в `settings` зашифрованным AES-GCM с `PANEL_MASTER_KEY`. Квоты уведомляют о пороге, исчерпании, сбросе и пополнении в человекочитаемых единицах.

### Аренда

Для маршрута хранится клиент, контакт, дата «оплачено до», флаг напоминания. Каждую полученную оплату администратор записывает с суммой, новой датой и примечанием. Общая сумма считается из `payments`. Автоматического выставления счёта и долга нет. В дату окончания после 09:00 местного времени при включённом напоминании отправляется одно сообщение Telegram. Продление даты сбрасывает маркер напоминания.

## Данные SQLite

Файл `panel.db` в `PANEL_DATA`; WAL, один writer у агента и отдельный read-only пул web. Modernc v1.46.2 включает SQLite 3.51.3 (исправление WAL-reset race); минимальная версия Go — 1.25. Формат существующих таблиц не меняется. Таблицы:

| Таблица | Данные |
| --- | --- |
| `routes` | SNI, upstream, TLS, tls_passthrough (default 0), пауза, лимиты, скорость, порог, накопленные байты, мониторинг |
| `periods` | Использование, пополнение и отправленные события по дневному/месячному ключу |
| `samples` | Приём и отдача по минутам, 90 дней |
| `settings` | Основной домен, fallback HTML, Telegram API/chat/encrypted token, timezone после restore |
| `route_meter_ids` | Устойчивая идентичность маршрута для direct, независимая от повторного использования integer ID |
| `direct_checkpoints` | Сохранённые bin/bout каждого worker/backend, атомарно с totals; неактивные записи — 48 часов |
| `rentals` | Клиент, контакт, оплачено до, флаг и дата последнего напоминания |
| `payments` | Сумма в центах USD, дата оплаты, новая дата продления, заметка |
| `request_totals` | Накопленные HTTP-счётчики с начала сбора |
| `request_samples` | Дельты запросов и ответов по минутам, 90 дней |

Схема создаётся при старте, миграции старой схемы выполняются в `migrateRouteMonitor` и `initFinance`. Изменение базы требует теста миграции и проверки на копии данных.

`initHistoryIndexes` идемпотентно добавляет индексы времени без изменения строк и формата backup.

## Панель и API

Обычный запуск бинарника запускает supervisor (`process.go`). Он поднимает `--agent` и `--web`, перезапускает упавший web без остановки трафика. Агент владеет relay/fallback, конфигом, изменениями настроек и единственным writer. API агента слушает только Unix `PANEL_DATA/agent.sock`, mode 0600; web публикует прежний HTTP 9389, локально обслуживает сессии/SPA/историю/CSV, остальные API передаёт агенту с сохранением Host/Origin/cookie. Агент повторно проверяет аутентификацию. `/internal/lease` недоступен через публичный web. Файловая блокировка `agent.lock` запрещает два writer-агента одного каталога. При выходе агента supervisor сначала закрывает web/его read-only соединения и только затем перезапускает агент, чтобы restore не оставил читателей старой БД. Полное завершение контейнера останавливает оба процесса.

Отдельный процесс `--watchdog` рядом с HAProxy (другой контейнер/служба, запускается и контролируется watch.sh) независимо от панели и SQLite проверяет lease direct-учёта. При устаревании успешного сбора более чем на 10 секунд, недоступности агента либо сохранения более `max(30s, 3×flushInterval)` переводит настроенные quota-backends в maintenance и закрывает их сессии через master CLI, включая старые workers. Начальное состояние quota-backend в сгенерированном конфиге — disabled; открывает его только collector. При недоступном Runtime API watchdog не может гарантировать отключение; это не замена строгого in-path quota. Политика извлекается из комментариев сгенерированного конфига, снятие лимита прекращает watchdog-ограничение. После восстановления только агент возвращает ready.

Панель — React/Vite SPA под `/admin/` с маршрутами `/`, `/servers`, `/servers/:id`, `/finance`, `/finance/:id`, `/settings`. Сервер отдаёт `index.html` для вложенных URL. Vite `base` сейчас фиксирован на `/admin/`.

Вход — секретный `PANEL_TOKEN` длиной минимум 24 символа; хранится SHA-256 hash в памяти. После входа выдаётся подписанная 24-часовая cookie (`HttpOnly`, `SameSite=Strict`). Mutating API дополнительно сверяет Origin, если он есть. Админка доступна по HTTP без TLS согласно требованию владельца. Публичный HTTP не шифрует токен, cookie, CSV и архивы.

Списки `/routes` и `/request-stats` сортируются по ID. UI опрашивает текущее состояние с паузой 2 секунды после завершения запроса, отменяет устаревшие запросы и приостанавливает polling в скрытой вкладке. Смена статуса/скорости не переставляет серверы. `GET /healthz` проверяет SQLite, локальные listeners и свежий результат настоящего TLS/HTTP-запроса fallback через 443 (проба раз в 15 секунд, timeout 5 секунд, успешный результат не старше 45 секунд). Три неудачи подряд сохраняют ограниченные файлы диагностики, максимум раз в 10 минут: `incident-latest.json`, `incident-goroutines.txt`, mode 0600. Автоматического рестарта из-за заполнения maxconn нет. `/system` и UI показывают занятость/пик внешнего frontend и состояние HTTPS-пробы. `/system` дополнительно сообщает uptime, goroutines, heap, активные relay-соединения и ожидания SQLite.

Основные endpoints под `/<secret_path>/api`:

| Endpoint | Назначение |
| --- | --- |
| `POST /login`, `POST /logout`, `GET /me` | Сессия |
| `GET/POST /routes`, `PUT/DELETE /routes/:id`, `POST /routes/:id/topup` | Маршруты и квоты |
| `GET/PUT /settings` | Домен, fallback HTML, Telegram |
| `POST /restart` | Подтверждённый полный перезапуск панели и HAProxy (`{"confirm":true}`), ответ 202 |
| `GET /history/:id`, `GET /history/all` | Трафик |
| `GET /request-stats`, `GET /request-history/:id`, `/all` | HTTP метрики |
| `GET/PUT /finance/:id`, `GET/POST /finance/:id/payments` | Аренда и оплаты |
| `GET /system` | CPU/RAM/swap/диск VPS |
| `GET /export/payments.csv`, `GET /export/traffic.csv` | CSV за период и маршрут |
| `GET /backup`, `POST /restore` | ZIP backup и восстановление |

Все endpoints кроме login/logout требуют валидную cookie. CSV и ZIP не кэшируются. Для экспортов параметры `from`, `to` (`YYYY-MM-DD`), `route_id`, для трафика ещё `period=day|hour`. Диапазон не длиннее года, сами минутные сэмплы хранятся 90 дней.

## Резервная копия и восстановление

`GET /backup` создаёт согласованную SQLite копию через `VACUUM INTO` и ZIP с `panel.db`, `certs/*.pem`, `manifest.json`. Подготовка ZIP выполняется в локальный файл 0600 под stateMu (контекст до 2 минут); stateMu освобождается до отправки клиенту (до 5 минут). CSV аналогично готовится в файл 0600 (SQL до 30 секунд), закрывает rows до отправки (до 2 минут), одновременно допускается одна CSV-выгрузка. Временные файлы удаляются при завершении обработчика. Это требует свободного места для snapshot + ZIP/CSV. Manifest включает формат, домен, timezone и Telegram bot token **в открытом виде** для переноса на другой `PANEL_MASTER_KEY`. Токен входа в архив не включён. Храните ZIP как секрет.

`POST /restore` принимает ZIP (до 512 MiB с лимитами на распаковку), проверяет SQLite `integrity_check`, нужные таблицы, маршруты, домен, timezone, PEM и переносит Telegram token в шифрование текущей установки. Архив кладётся в staging, создаётся `restore.pending`, HTTP отвечает 202 и процесс завершается. Встроенный supervisor сначала останавливает web, затем перезапускает агент. До открытия SQLite `applyPendingRestore` переносит прежнюю БД/сертификаты в `before-restore-*`, ставит новые и удаляет маркер. После восстановления для входа используется токен текущего сервера. Стандартный запуск бинарника уже включает supervisor; роли `--agent`/`--web` отдельно вручную не запускают.

## Пределы текущей реализации

- Direct обеспечивает только мягкие квоты с явно включённым direct_limits. Перерасход зависит от нагрузки, contstats и задержки опроса/команд; при сбое Runtime API строгой верхней границы нет. Crash/hard-stop может потерять несохранённый хвост. Relay остаётся строгим режимом.
- Полный перезапуск: авторизованный API сначала проверяет сохранение счётчиков, отвечает 202 и вызывает штатное завершение Go. main останавливает relay, закрывает HAProxy-сессии, снимает остаток счётчиков, flush и создаёт `haproxy.restart-request`. Watcher перезапускает master/workers **в том же** контейнере/network namespace. Встроенный supervisor перезапускает web и агент; Docker/systemd страхуют сам supervisor. VPS не перезагружается.

- HTTP админка не обеспечивает конфиденциальность канала; TLS на 443 относится к проксируемым доменам, не к порту 9389.
- Самоподписанные сертификаты потребуют ручного доверия клиентов.
- HTTP метрики агрегированы по backend; журнал отдельных URL, методов и IP клиентов не хранится.
- До первого опроса HAProxy после включения статистики исторических HTTP счётчиков нет.
- CPU/RAM/диск относятся к VPS с панелью, не к конечным серверам.
- TCP мониторинг проверяет доступность порта, не полноценность приложения.
- Секретный путь `/admin/` в Vite задан на этапе сборки.
