# Архитектура FluxGate

## Назначение

FluxGate — самостоятельная панель аренды и управления SNI-прокси. На одном VPS работают Go-сервис панели/учёта трафика и HAProxy. Администратор добавляет конечные HTTP или HTTPS серверы по IP и порту, назначает точный SNI или wildcard третьего уровня, управляет доступом, квотами, скоростью, мониторингом, арендой и Telegram-уведомлениями.

## Путь пользовательского трафика

`settings.proxy_mode` выбирает `relay` (по умолчанию для старых и новых баз) или `direct`. API сохраняет режим вместе с остальными настройками транзакционно; при ошибке валидации/SQL восстанавливает прежние in-memory настройки и конфиг. `PUT /settings` без `proxy_mode` сохраняет прежний режим. Далее сначала описан relay.

```text
Клиент TLS/HTTP/WS → :443 HAProxy public_sni (TCP, читает SNI)
  → relay_<id> 127.0.0.1:10000+id (Go: квота, скорость, счётчики)
  → HAProxy internal_tls 127.0.0.1:8443 (TLS terminate, HTTP)
  → target_<id> IP:port (HTTP/HTTPS, WS upgrade)
```

Основной домен и незнакомый SNI идут через `relay_fallback` 127.0.0.1:9999 к `internal_tls`, затем к `fallback_page` 127.0.0.1:8181. Внутренние порты доступны только локально. `public_sni` принимает все интерфейсы на 443. Панель отдельно слушает 9389 и не проходит через HAProxy.

`config.go` строит ACL, размещая точные имена перед wildcard. В fallback входит главный домен; значение можно менять в настройках. Конфиг сначала пишется во временный файл, проверяется `haproxy -c`, затем атомарно заменяет `haproxy.cfg`. Watcher замечает изменение и плавно перезапускает HAProxy. Go создаёт self-signed ECDSA P-256 сертификат на каждый SNI и fallback; клиентам требуется доверять ему самостоятельно. TLS-проверка upstream опциональна.

### Счётчики, квоты и скорость

#### Прямой режим

В `direct` работает единственный `public_direct` HTTP frontend с TLS на `:443`: `клиент → HAProxy → direct_<id>_<meterID> → upstream`. Сертификаты и ACL `ssl_fc_sni` те же; основной и неизвестный домены идут к `fallback_page :8181`. `internal_tls :8443` и relay backend отсутствуют. Неиспользуемые Go listeners остаются локальными для обратного переключения; данные через них не идут. Глобальный HAProxy maxconn равен N+reserve вместо 2N+reserve. HTTP/WebSocket и upstream TLS verification сохраняются.

В direct лимиты/скорость **не применяются**. UI отключает их редактирование/пополнение и показывает предупреждение, API status не выставляет `quota`. Периоды и totals продолжают накапливаться согласно `count_mode`; quota-уведомления от direct отключены. При возврате на relay сохранённые лимиты применяются к накопленному использованию. Пауза выдаёт 503 в HAProxy; collector переводит сервер в maintenance и закрывает сессии на старых workers. Смена режима принудительно завершает соединения прежнего режима после применения конфига/ближайшего опроса (обычно 1–3 секунды); обычные reload сохраняют туннели.

`direct.go` опрашивает `bin`/`bout` backend через Runtime API каждую секунду. `option contstats` обновляет незакрытые потоки примерно раз в 5 секунд; скорость — средняя за 10 секунд. Это HTTP/WS-байты, не TLS/TCP/IP. История двух режимов не пересчитывается задним числом и не идентична счётчику всего порта/провайдера. См. [HAProxy contstats](https://docs.haproxy.org/3.2/configuration.html#4-option%20contstats).

Worker определяется по node, Start_time_sec и PID (нужен HAProxy 3.2). Независимый 128-битный `route_meter_ids.token` не позволяет при повторном использовании SQLite route ID присвоить старый трафик новому серверу. Панель держит интерактивный stats connection к каждому обнаруженному worker; этот connection удерживает softly stopped worker до нуля клиентских соединений и сохранения финальных счётчиков. Watcher перед reload ждёт `haproxy.reload-ready` на новый nonce из `haproxy.reload-request`. Если панель не отвечает, старый конфиг продолжает работать, reload повторяется позже. Ручной reload в обход watcher не даёт этой гарантии.

Дельты добавляются в память маршрутов; `direct_checkpoints` и totals/periods/samples фиксируются **одной** транзакцией в `accounting.go`. Ошибка commit не продвигает долговечный checkpoint; после рестарта панели счётчик продолжается, а не берётся заново целиком. Неактивные checkpoints удаляются через 48 часов. После рестарта только панели старые живые workers дополнительно опрашиваются через master CLI; возможна потеря хвоста worker, завершившегося до следующего опроса. Crash/hard-stop HAProxy может потерять ещё не снятые байты, а отказ диска расширяет окно потери. Это не журнал финансового биллинга с гарантией нулевой потери при аварии.

`RouteState.mu` не удерживается во время Runtime API/SQL. Stats connections принадлежат одному фиксированному worker; ошибки ограничены по времени и логируются не чаще раза в минуту. `/system` показывает время последнего успешного чтения и ошибки; UI предупреждает о задержке статистики.

#### Режим relay

Go relay считает байты TLS-потока (включая TLS-заголовки, без TCP/IP). Для маршрута выбирается учитываемое направление: `up` (приём), `down` (отдача), `both`. Дневная квота сбрасывается в 00:00 `PANEL_TIMEZONE`. Месячная начинается в день создания маршрута, при отсутствии числа используется последний день месяца. Пополнение `topup` увеличивает только текущий период. После лимита текущие соединения закрываются, следующие запросы получают 429. Пауза даёт 503. Общая скорость маршрута ограничивается token bucket по направлениям.

`relay.go` передаёт блоки через переиспользуемые буферы 16 KiB (32 KiB на двухсторонний туннель). Ошибки закрывают обе стороны и отменяют ожидание limiter; чистый EOF сохраняет TCP half-close до завершения ответа. Неактивные чтения/записи ограничены 1 часом. Квота резервируется до записи, а учитываются фактически записанные байты. Незавершённые записи при смене дня/месяца относятся к исходному периоду. Новые заблокированные соединения получают ограниченный по времени TLS/HTTP-ответ 429/503 от relay, без ожидания reload HAProxy.

Путь проходит через два frontend одного HAProxy. `PANEL_MAX_CONNECTIONS` задаёт внешний лимит N (по умолчанию 10000); внутренний лимит — N+reserve, общий — 2N+reserve, reserve=max(8,min(256,N/10)). Внешние pending handshakes не могут занять все места внутреннего входа. После лимита новые клиенты ожидают в системной очереди; это ограничение одновременно открытых соединений, не Мбит/с. ClientHello должен поступить за 5 секунд, иначе `WAIT_END` отклоняет поток. Внутренний TLS/HTTP клиент имеет idle timeout 30 секунд, WebSocket tunnel — 1 час.

`accounting.go` раз в `PANEL_FLUSH_INTERVAL` (по умолчанию 5 секунд) сохраняет изменившиеся `routes`, `periods` и дельты `samples` одной транзакцией для всех маршрутов. Во время SQL блокировки relay не удерживаются. Буфер дельт уменьшается только после успешного commit; ошибка БД приводит к повтору без потерь и удвоения. Скорость рассчитывается независимым секундным worker по реальному интервалу. SIGTERM/SIGINT закрывают listeners и соединения, дожидаются goroutines и сохраняют остаток перед закрытием SQLite. Backup также начинается с сохранения остатка. При аварии теряются данные после последнего успешного commit. UI запрашивает `historyAPI` и агрегирует до 60 точек.

HTTP-метрики сохраняются общей транзакцией раз в 10 секунд; baseline продвигается только после успешного commit. Индексы `samples(ts)` и `request_samples(ts)` ускоряют общую историю и очистку. WAL и `SetMaxOpenConns(1)` сохранены. Контрольные изменения и сохранение сериализованы через `stateMu`; `RouteState.mu` защищает короткие операции в памяти. Медленная БД может задержать API/историю, но не должна блокировать передачу данных.

`history.go` кэширует только готовые агрегированные графики на 30 секунд (до 64 ключей), объединяя одновременные одинаковые запросы через отменяемую очередь. Запрос/ожидание ограничены 10 секундами и контекстом HTTP-клиента. Создание/удаление маршрута меняет epoch кэша, чтобы переиспользование ID не выдавало прежнюю историю. Retention остался 90 дней: раз в минуту удаляются пакеты до 5000 строк, максимум 8 пакетов на таблицу за запуск с общим бюджетом 2 секунды; backlog продолжается в следующий запуск. Текущие totals, квоты и платежи не затрагиваются.

HAProxy конфигурация строится из снимков маршрутов под mutex, с детерминированной сортировкой и ID как последним критерием. Идентичный файл не переписывается. Watcher запускает один master-worker и отправляет master SIGUSR2 для reload, передаёт TERM/INT и сообщает об неожиданном завершении master. Старые workers завершаются после закрытия соединений; `hard-stop-after 1h` ограничивает draining. Соединения на старом worker через час после reload будут закрыты. См. [HAProxy management guide](https://docs.haproxy.org/3.2/management.html).

### HTTP-запросы

`requeststats.go` каждые 10 секунд читает HAProxy Runtime API `show stat` из Unix socket. Для backend `target_<id>` (relay) или `direct_<id>_<meterID>` берутся `req_tot`, ответы 2xx/3xx/4xx/5xx, активные соединения и среднее время ответа. Дельты записываются в `request_samples` и `request_totals`; первый снимок служит baseline, так как HAProxy уже мог обслуживать трафик до запуска панели. После reload HAProxy уменьшение счётчика трактуется как сброс. Эти HTTP-метрики опрашивают только текущий worker, в отличие от direct-учёта байтов всех workers; для строгого подсчёта запросов через reload они не предназначены. График показывает историю с момента включения сбора, не восстанавливает прошлые запросы из TLS-байтов. Счётчик активных соединений может включать длительные WebSocket-сеансы.

### Мониторинг и уведомления

TCP проверка IP:port выполняется примерно раз в 10 секунд; опциональное Telegram-уведомление отправляется через 5 минут непрерывной недоступности, затем при восстановлении. Это проверка доступности порта, не HTTP-ответа. Telegram API может указывать на HTTPS-зеркало. Bot token хранится в `settings` зашифрованным AES-GCM с `PANEL_MASTER_KEY`. Квоты уведомляют о пороге, исчерпании, сбросе и пополнении в человекочитаемых единицах.

### Аренда

Для маршрута хранится клиент, контакт, дата «оплачено до», флаг напоминания. Каждую полученную оплату администратор записывает с суммой, новой датой и примечанием. Общая сумма считается из `payments`. Автоматического выставления счёта и долга нет. В дату окончания после 09:00 местного времени при включённом напоминании отправляется одно сообщение Telegram. Продление даты сбрасывает маркер напоминания.

## Данные SQLite

Файл `panel.db` в `PANEL_DATA`; включены WAL и один connection pool. Таблицы:

| Таблица | Данные |
| --- | --- |
| `routes` | SNI, upstream, TLS, пауза, лимиты, скорость, порог, накопленные байты, мониторинг |
| `periods` | Использование, пополнение и отправленные события по дневному/месячному ключу |
| `samples` | Приём и отдача по минутам, 90 дней |
| `settings` | Основной домен, fallback HTML, Telegram API/chat/encrypted token, timezone после restore |
| `route_meter_ids` | Устойчивая идентичность маршрута для direct, независимая от повторного использования integer ID |
| `direct_checkpoints` | Сохранённые bin/bout каждого worker/backend, атомарно с totals; неактивные записи — 48 часов |
| `rentals` | Клиент, контакт, оплачено до, флаг и дата последнего напоминания |
| `payments` | Сумма в центах USD, дата оплаты, новая дата продления, заметка |
| `request_totals` | Накопленные HTTP-счётчики с начала сбора |
| `request_samples` | Дельты запросов и ответов по минутам, 90 дней |

Схема создаётся при старте, миграции старой схемы выполняются в `migrateRouteMonitor` и `initFinance`. Изменение базы требует теста миграции и проверки на копии данных.

`initHistoryIndexes` идемпотентно добавляет индексы времени без изменения строк и формата backup.

## Панель и API

Панель — React/Vite SPA под `/admin/` с маршрутами `/`, `/servers`, `/servers/:id`, `/finance`, `/finance/:id`, `/settings`. Сервер отдаёт `index.html` для вложенных URL. Vite `base` сейчас фиксирован на `/admin/`.

Вход — секретный `PANEL_TOKEN` длиной минимум 24 символа; хранится SHA-256 hash в памяти. После входа выдаётся подписанная 24-часовая cookie (`HttpOnly`, `SameSite=Strict`). Mutating API дополнительно сверяет Origin, если он есть. Админка доступна по HTTP без TLS согласно требованию владельца. Публичный HTTP не шифрует токен, cookie, CSV и архивы.

Списки `/routes` и `/request-stats` сортируются по ID. UI опрашивает текущее состояние с паузой 2 секунды после завершения запроса, отменяет устаревшие запросы и приостанавливает polling в скрытой вкладке. Смена статуса/скорости не переставляет серверы. `GET /healthz` — отдельная публичная проверка SQLite и локальных портов/сокета HAProxy без выдачи настроек. `/system` дополнительно сообщает uptime, goroutines, heap, активные relay-соединения и ожидания SQLite.

Основные endpoints под `/<secret_path>/api`:

| Endpoint | Назначение |
| --- | --- |
| `POST /login`, `POST /logout`, `GET /me` | Сессия |
| `GET/POST /routes`, `PUT/DELETE /routes/:id`, `POST /routes/:id/topup` | Маршруты и квоты |
| `GET/PUT /settings` | Домен, fallback HTML, Telegram |
| `POST /restart` | Подтверждённый полный перезапуск панели и HAProxy (`{"confirm":true}`), ответ 202 |
| `GET /history/:id`, `GET /history/all` | Трафик |
| `GET /request-stats`, `GET /request-history/:id`, `/all` | HTTP метрики |
| `GET/PUT /finance/:id`, `GET/POST /finance/:id/payments` | Аренда и оплаты |
| `GET /system` | CPU/RAM/swap/диск VPS |
| `GET /export/payments.csv`, `GET /export/traffic.csv` | CSV за период и маршрут |
| `GET /backup`, `POST /restore` | ZIP backup и восстановление |

Все endpoints кроме login/logout требуют валидную cookie. CSV и ZIP не кэшируются. Для экспортов параметры `from`, `to` (`YYYY-MM-DD`), `route_id`, для трафика ещё `period=day|hour`. Диапазон не длиннее года, сами минутные сэмплы хранятся 90 дней.

## Резервная копия и восстановление

`GET /backup` создаёт согласованную SQLite копию через `VACUUM INTO` и ZIP с `panel.db`, `certs/*.pem`, `manifest.json`. Подготовка ZIP выполняется в локальный файл 0600 под stateMu (контекст до 2 минут); stateMu освобождается до отправки клиенту (до 5 минут). CSV аналогично готовится в файл 0600 (SQL до 30 секунд), закрывает rows до отправки (до 2 минут), одновременно допускается одна CSV-выгрузка. Временные файлы удаляются при завершении обработчика. Это требует свободного места для snapshot + ZIP/CSV. Manifest включает формат, домен, timezone и Telegram bot token **в открытом виде** для переноса на другой `PANEL_MASTER_KEY`. Токен входа в архив не включён. Храните ZIP как секрет.

`POST /restore` принимает ZIP (до 512 MiB с лимитами на распаковку), проверяет SQLite `integrity_check`, нужные таблицы, маршруты, домен, timezone, PEM и переносит Telegram token в шифрование текущей установки. Архив кладётся в staging, создаётся `restore.pending`, HTTP отвечает 202 и процесс завершается. systemd или Docker его перезапускает. До открытия SQLite `applyPendingRestore` переносит прежнюю БД/сертификаты в `before-restore-*`, ставит новые и удаляет маркер. После восстановления для входа используется токен текущего сервера. При нестандартном развертывании без автоматического рестарта сервис нужно запустить вручную.

## Пределы текущей реализации

- Direct не обеспечивает квоты и rate limiting; режим всегда выбирается явно, при обновлении по умолчанию остаётся relay.
- Полный перезапуск: авторизованный API сначала проверяет сохранение счётчиков, отвечает 202 и вызывает штатное завершение Go. main останавливает relay, закрывает HAProxy-сессии, снимает остаток счётчиков, flush и создаёт `haproxy.restart-request`. Watcher перезапускает master/workers **в том же** контейнере/network namespace. Go возвращается через Docker/systemd supervisor. Без него ручной запуск не возобновится. VPS не перезагружается.

- HTTP админка не обеспечивает конфиденциальность канала; TLS на 443 относится к проксируемым доменам, не к порту 9389.
- Самоподписанные сертификаты потребуют ручного доверия клиентов.
- HTTP метрики агрегированы по backend; журнал отдельных URL, методов и IP клиентов не хранится.
- До первого опроса HAProxy после включения статистики исторических HTTP счётчиков нет.
- CPU/RAM/диск относятся к VPS с панелью, не к конечным серверам.
- TCP мониторинг проверяет доступность порта, не полноценность приложения.
- Секретный путь `/admin/` в Vite задан на этапе сборки.
