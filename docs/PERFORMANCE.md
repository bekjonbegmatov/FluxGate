# Разбор деградации со временем

Проверка 2026-09-29. Причину инцидента на рабочем сервере без его снимка метрик установить нельзя. График сетевого трафика отражает реально переданные байты, а не предельную пропускную способность. Ниже — воспроизведённые дефекты кода, не утверждение о содержимом недоступного VPS.

## 1. Общий лимит двух входов HAProxy

Один запрос занимает две frontend-сессии: public_sni → Go → internal_tls. Прежде был только global maxconn=20000. Внешние соединения могли занять места, необходимые для собственного внутреннего TLS-этапа. Получается ожидание при низкой загрузке CPU, затрагивающее также fallback. Согласно [документации HAProxy](https://docs.haproxy.org/3.2/configuration.html#3.2-maxconn), достижение global maxconn останавливает приём соединений.

В изолированном тесте уменьшили общий лимит до 32 и сначала открыли 24 внешних TCP-соединения. После одновременной отправки TLS завершились только 8 внутренних туннелей, которые остались открыты; остальные не могли завершить handshake. С внешним лимитом 16, внутренним 24 и общим 40 завершились все 16 допущенных туннелей. Остальные ожидают внешней очереди, а не занимают внутренние slots. Нормальная конфигурация: 10000/10256/20256 соответственно.

Дополнительно входы без ClientHello ограничены 5 секундами. Проверено шестью молчащими TCP-клиентами. Внутренний idle timeout клиента TLS/HTTP — 30 секунд, WebSocket — 1 час. Необходимую ёмкость нужно оценивать по одновременным соединениям и памяти, не только Мбит/с.

## 2. Память открытых туннелей

Два буфера по 64 KiB удерживались на всём протяжении соединения, даже когда оно простаивало. Тест на 256 idle-туннелей подтвердил 32 MiB только буферов (без сокетов, горутин, HAProxy и TLS). При 10000 это 1250 MiB. Новые буферы 16 KiB дают 8 MiB на 256 туннелей, 312.5 MiB на 10000. Рост количества подключений мог приводить к swap при небольшой загрузке CPU; был ли swap в конкретном инциденте, неизвестно.

## 3. SQLite и медленные клиенты панели

- Отменённые HTTP-запросы истории продолжали ожидать единственный DB connection. Тест воспроизвёл это при занятом connection. Теперь QueryContext отменяет очередь и запрос, общий deadline — 10 секунд.
- CSV отправлялся непосредственно из открытых rows. Остановив получателя на первом Write, тест получил timeout другого DB-запроса. Теперь SQL закрывается после подготовки частного временного CSV, до отправки.
- Добавление маршрута удерживало App.mu во время ожидания SQL; эта же блокировка нужна fallback-странице. Убрано ожидание SQLite под App.mu, отдельный regression-тест проверяет доступность читателей при занятой БД.
- Backup удерживал stateMu во время сетевой отправки. Теперь блокировка освобождается после подготовки файла. Тест медленного получателя проверяет, что flushTraffic продолжает сохранять новые байты.
- Массовое удаление истёкшей истории заменено небольшими транзакциями с бюджетом времени. Политика 90 дней не сокращена, totals/платежи не удаляются.

Схема SQLite не менялась, переключение на другую СУБД не требуется для этих исправлений. На этом этапе WAL и один connection были сохранены; следующее обновление выделяет отдельный read-only пул, см. ниже. [SQLite WAL](https://sqlite.org/wal.html) поддерживает конкурентные чтения/запись, но удержание единственного connection самим приложением всё равно создаёт очередь. Смена СУБД не исправила бы лимиты HAProxy и память Go.

## Проверки и границы результатов

`go test -race ./...`, `go vet ./...`, `python3 deploy/test-update.py` и полный Docker TLS-тест. Отдельные opt-in benchmarks:

```bash
go test ./cmd/panel -run '^$' -bench 'BenchmarkHistoryGrowth|BenchmarkRelayTCP' -benchtime=1s
python3 deploy/test-integration.py --seconds 300 --history-days 90
```

На Apple M2, локально, искусственная история 20 маршрутов: холодный запрос за 1 день около 15 ms, за 90 дней (2 592 000 строк samples) около 3.19 s. Это демонстрирует рост стоимости больших диапазонов, но не доказывает влияние на конкретный сервер с историей в несколько дней. Кэш на 30 секунд хранит лишь готовые графики (не более 64 ключей), ускоряя повторные запросы; холодный запрос остаётся ограничен 10 секундами.

Пятиминутный тест TLS в Linux Docker с четырьмя потоками после исправления лимитов и буферов: среднее 7.556 Gbit/s; в конце 18 Go goroutines, 0 активных route relay-соединений. Это синтетический локальный тест, не замер интернет-канала и не гарантия многосуточной стабильности. Сравнивать абсолютные значения между запусками с другой фоновой нагрузкой некорректно.

Отдельный финальный прогон: 120 секунд TLS параллельно опросу графиков, 90 дней синтетической истории для 3 маршрутов (по 388803 строки в каждой таблице, около 47 MB основной БД). Среднее 7.849 Gbit/s, ошибок сохранения не зарегистрировано, после нагрузки 18 goroutines и 0 route relay-соединений. Пара графиков вместе с `/system` занимала 0.83–1.21 s при пересчёте и 10–37 ms из кэша. Файл WAL около 47.5 MB после генерации истории оставался переиспользуемым: размер файла WAL сам по себе не равен объёму незафиксированных данных и не доказывает неисправность.

## Что нужно с работающего сервера

Разовый `deploy/diagnose.py` до перезагрузки: фактически запущенные image ID, CPU/RAM/OOM, текущие/max HAProxy-сессии, размеры БД/WAL, очередь/ошибки сохранения, swap/iowait и сводка TCP. Скрипт работает и со старой версией панели, не меняет настройки или данные и не печатает секреты. По результату можно отличить насыщение соединений от SQLite, сети, upstream или ресурсов хоста. Без этого нельзя обещать, что все причины конкретного инцидента устранены.

## Прямой режим и полный перезапуск

Дополнительный прогон 2026-09-29 проверил direct HTTPS, неприменение квот/limiter, ноль route relay-соединений, непрерывный учёт WebSocket, три graceful reload, перезапуск только панели с продолжающимся старым worker, паузу, полный перезапуск панели/HAProxy и возврат на relay с восстановлением квот. Проверены недоступность restart API без авторизации и сохранение выбранного режима/счётчиков после перезапуска. Тесты SQLite проверяют атомарный rollback checkpoints вместе с totals, отсутствие повторного учёта и переиспользование route ID.

Локальный direct HTTPS-тест в Docker (4 потока, 20 секунд) дал среднее 7.209 Gbit/s. Следующий 60-секундный relay-прогон с опросом истории — 4.619 Gbit/s. Повторный финальный прогон: direct 7.607 Gbit/s, relay 6.914 Gbit/s, запросы графиков 8–21 ms; в конце 19 goroutines и 0 route relay-соединений. Это не контролируемое A/B-сравнение: фоновая нагрузка машины менялась; из этих чисел нельзя выводить коэффициент ускорения или обещать результат на выделенном сервере. Длительная стабильность на реальном канале требует наблюдения там.

Расхождение панели и провайдера около ×2 само по себе не доказывает потерю учёта: клиентские байты проходят внешний порт дважды (upstream → прокси → клиент), если считать RX+TX. Сравнивать надо одинаковый период и одинаковые единицы. UI исправляет двоичные TB/GB на TiB/GiB; totals не умножаются искусственно. CPU теперь отдельно от iowait/steal, softirq показан как часть CPU. Без процессных метрик нельзя приписывать показанные на скриншоте 91.8% SQLite или Go.

## Повторный инцидент 443 и обновление архитектуры

Проверка 2026-09-30. Полученный снимок был снят **после перезапуска**, уже в direct, не во время сбоя relay. В нём база меньше 1 MiB, WAL около 2 MiB, суммарное ожидание SQLite около 4 ms, последнее сохранение около 10 ms без ошибок. Он не подтверждает гипотезу об узком месте SQLite. Примерно 5000 текущих и 8000 пиковых соединений при лимите 10000 требуют наблюдения, но не доказывают насыщение в момент сбоя. Поднимать лимит до 20000 допустимо конфигурацией, однако это не устраняет накопление зависших соединений. Источник недоступности именно рабочего VPS пока не установлен.

### Воспроизведённое зависание relay после закрытия клиента

TLS/WebSocket-клиент закрывал транспорт без корректного завершения протокола. Go уже отпускал relay, но после его преждевременного TCP half-close внутренний TLS frontend HAProxy мог оставлять upgraded upstream занятым до часового timeout. После нескольких reload это удерживало старые workers. Сценарий воспроизведён на штатном TCP-пути; смена внутреннего транспорта на Unix не вошла в обновление.

Исправление: после EOF внешнего TLS-потока relay не отправляет ранний FIN внутреннему TLS frontend. Вместо этого ответ дренируется с 30-секундным **idle**, а не общим timeout; активная передача продолжает обновлять deadline. На ошибке/истечении ожидания внутренняя сторона сбрасывается. Обычный TCP half-close в низкоуровневых тестах сохранён. Тест проверяет завершение старых workers, полный размер HTTP-ответов, продолжающийся WebSocket при reload и сохранение строгой relay-квоты. Это подтверждённый дефект кода, но без снимка реального сбоя нельзя приписать ему весь инцидент.

### Изоляция панели, учёта и контроля квот

- Web и traffic agent — отдельные процессы с отдельными heaps. Тест убивает только web и проверяет, что текущий relay/WebSocket продолжает передавать байты, а PID агента не меняется. Supervisor восстанавливает web. Перед заменой базы при restore он закрывает все readers; реальное восстановление ZIP проверено интеграционно.
- Единственный writer принадлежит агенту. Web читает историю/CSV через отдельный read-only пул до 4 connections; тест удерживает незавершённую запись и подтверждает независимое чтение WAL, а запись через любой reader запрещена. SQLite обновлена до 3.51.3, содержащей [исправление WAL-reset race](https://sqlite.org/wal.html#walresetbug); это профилактика для нескольких соединений, не доказанная причина прежнего сбоя.
- Collector direct не ждёт SQL/stateMu. Тест блокирует writer, снимает новые счётчики и проверяет, что checkpoint сохраняется атомарно с соответствующими totals, а пришедшая во время commit дельта остаётся для следующей записи. Проверено сохранение байтов при rollback удаления маршрута.
- Direct-квоты включаются отдельно и остаются мягкими. Дневная/месячная граница, пополнение, общий bandwidth limit четырёх потоков и WebSocket проверены на настоящем HAProxy. При зависании агента **и всего контейнера panel** внешний watchdog закрывает quota-маршруты, включая туннель на старом worker; неограниченный маршрут продолжает отвечать.
- У stopped backend HAProxy отвергает server-команды, даже если streams живы. Для этого случая используется фильтрованный список streams и адресное завершение по проверенным ID через [Runtime API](https://docs.haproxy.org/3.2/management.html#9.3). Таймаут recv теперь считается провалом теста, а не доказательством закрытия. Это также исправляет паузу старого direct-туннеля после перезапуска панели.

Добавлена настоящая локальная TLS/HTTP-проба fallback на 443 и ограниченная запись incident JSON/stack после трёх неудач; UI показывает текущие/пиковые соединения и свежесть ответа. Это диагностика, не автоматический restart или обещание доступности через внешний firewall. История остаётся 90-дневной; часовые rollups, PostgreSQL/Redis и переписывание relay в один TLS frontend в это обновление не включены.

### Результаты новых прогонов

Пятиминутный relay-прогон с 90 днями истории (по ~389 тысяч строк traffic/request history для трёх маршрутов): среднее 4.702 Gbit/s, после нагрузки 23 goroutines агента и 0 активных route relay-соединений. В одном таком прогоне HAProxy вывел предупреждение внутреннего watchdog с попыткой восстановления потока; причина этой задержки на локальном Docker-хосте не установлена. Этот замер нельзя представлять как доказательство отсутствия зависаний или многосуточной стабильности.

Итоговый полный прогон после исправления отключения stopped-backends и усиления тестов: direct 20 секунд — 7.729 Gbit/s, relay 60 секунд — 5.787 Gbit/s; 90 дней истории, 21 goroutine агента и 0 route relay-соединений в конце. Суммарный опрос пары графиков с /system занимал 13 ms–1.39 s; ошибок сохранения тест не обнаружил. Четыре одновременные загрузки суммарно 512 KiB при общем direct-лимите 128 KiB/s заняли 4.34 s. Подтверждены закрытие старого direct-туннеля при паузе/reload и защита при замороженном контейнере, не только ответы 503 новым клиентам.

Числа получены на локальном Linux Docker, не на целевом выделенном сервере, и не являются контролируемым сравнением производительности версий. Базовые проверки: `go test -race ./...`, `go vet ./...`, frontend build, bash syntax, `git diff --check`, 8 тестов updater. Для эксплуатационного подтверждения нужны метрики до рестарта при следующем реальном сбое и длительное наблюдение на VPS.

## Поддержка настраиваемого потолка 100k

Лимит поднят с 20000 до 100000, default остаётся 10000. Это диапазон конфигурации, **не результат нагрузочного теста на 100k**. По просьбе владельца рабочий компьютер не используется для тяжёлого stress: `--functional-only` пропускает throughput и генерацию истории, тестовые контейнеры имеют ограничения CPU, Go tests/build выполняются с ограниченным параллелизмом.

Основания решений: [HAProxy maxconn/FD](https://docs.haproxy.org/3.2/configuration.html#3.2-maxconn), [Linux ip_local_port_range](https://kernel.org/doc/html/latest/networking/ip-sysctl.html), [реализация Unix listeners в HAProxy 3.2](https://github.com/haproxy/haproxy/blob/v3.2.0/src/sock_unix.c). Сторонний исходный код не копировался. Замена SQLite/PostgreSQL не расширяет TCP tuple space и не исправляет лимиты дескрипторов.

Изменения:

- HAProxy→relay: приватный Unix stream на маршрут, без конечного TCP-пула 127.0.0.1:10000+id.
- Relay→internal TLS: 16 loopback destination ports 8443–8458. Короткая критическая секция выбирает минимум активных соединений, равные — по кругу; освобождение после close/dial error. SQL и network не входят в mutex. Так разные длительности сессий не закрепляют новые подключения за перегруженным портом.
- Полностью Unix-вариант проверен и отвергнут: после pause/закрытия внешнего TLS/WS Go имел 0 соединений, но внутренний HAProxy stream удерживал upstream и старый worker до 1h. На TCP возврате сохранён abortive close RST; повторный протокольный тест подтвердил завершение старых workers. Это воспроизведение на стенде, не доказательство причины прежнего production-инцидента.
- HAProxy relay cap 100000/100256/200256, direct 100000/100256; FD limits 1048576. В Go admission применяется до goroutine/dial и суммарно охватывает поколения/маршруты. Лимит отказывает только новым подключениям, не закрывает действующие.
- Docker расширяет ephemeral range до 10000–65535 только в своём network namespace. Внешний upstream по-прежнему имеет предел исходящих портов: для 100k к одному сервису нужны дополнительные реальные endpoints или исходящие IP/NAT. Смена доменных имён к тому же endpoint не помогает.
- Direct stopped-worker shutdown использует пакеты до 64 проверенных IDs, а не один Runtime API round trip на сессию; ответы и размер списка ограничены, неизвестные ответы — ошибка. Это важно для больших списков, но задержка отключения 100k не измерялась.
- FD диагностика не сортирует сотни тысяч записей каждые 2 секунды: счёт страницами, кэш 30 секунд. Heap через runtime/metrics, без ReadMemStats на каждом UI poll.
- Updater `--max-connections` сохраняет старую .env до повышения, делает live ZIP и при неудаче возвращает env/образы. Тот же data volume сохраняется; автоматического удаления данных/импорта устаревшего snapshot нет.

На конфиге 100k проверяется запуск настоящего HAProxy 3.2.25 **при малом числе клиентов**, TLS/WS, reload, корректное освобождение relay/старых workers, строгие relay-квоты, мягкие direct-квоты/watchdog, web/agent/container restart, backup и restore. Алгоритмы допуска/распределения и границы 1–100000 проверяются unit/race tests без создания 100k sockets. Контроль именно вместимости 40–100k, CPU/RAM/TLS, исходящих портов и длительной стабильности остаётся задачей отдельного стенда, а не обещанием для i7-8700/32 GB.

Итоговые функциональные прогоны прошли, в том числе batch-отключение трёх старых direct-туннелей после restart панели и при замороженном контейнере (watchdog). Выполнены go test, race, vet, frontend build, bash syntax, git diff --check и 11 тестов updater. Ошибочный полностью Unix-прототип не включён в выпуск. Throughput, большая история и 100k реальных клиентов в этом обновлении намеренно не тестировались.
