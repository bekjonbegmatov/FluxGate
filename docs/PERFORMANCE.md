# Разбор деградации со временем

Проверка 2026-09-29. Причину инцидента на рабочем сервере без его снимка метрик установить нельзя. График сетевого трафика отражает реально переданные байты, а не предельную пропускную способность. Ниже — воспроизведённые дефекты кода, не утверждение о содержимом недоступного VPS.

## 1. Общий лимит двух входов HAProxy

Один запрос занимает две frontend-сессии: public_sni → Go → internal_tls. Прежде был только global maxconn=20000. Внешние соединения могли занять места, необходимые для собственного внутреннего TLS-этапа. Получается ожидание при низкой загрузке CPU, затрагивающее также fallback. Согласно [документации HAProxy](https://docs.haproxy.org/3.2/configuration.html#3.2-maxconn), достижение global maxconn останавливает приём соединений.

В изолированном тесте уменьшили общий лимит до 32 и сначала открыли 24 внешних TCP-соединения. После одновременной отправки TLS завершились только 8 внутренних туннелей, которые остались открыты; остальные не могли завершить handshake. С внешним лимитом 16, внутренним 24 и общим 40 завершились все 16 допущенных туннелей. Остальные ожидают внешней очереди, а не занимают внутренние slots. Нормальная конфигурация: 10000/10256/20256 соответственно.

Дополнительно входы без ClientHello ограничены 5 секундами. Проверено шестью молчащими TCP-клиентами. Внутренний idle timeout клиента TLS/HTTP — 30 секунд, WebSocket — 1 час. Необходимую ёмкость нужно оценивать по одновременным соединениям и памяти, не только Мбит/с.

## 2. Память открытых туннелей

Два буфера по 64 KiB удерживались на всём протяжении соединения, даже когда оно простаивало. Тест на 256 idle-туннелей подтвердил 32 MiB только буферов (без сокетов, горутин, HAProxy и TLS). При 10000 это 1250 MiB. Новые буферы 16 KiB дают 8 MiB на 256 туннелей, 312.5 MiB на 10000. Рост количества подключений мог приводить к swap при небольшой загрузке CPU; был ли swap в конкретном инциденте, неизвестно.

## 3. SQLite и медленные клиенты панели

- Отменённые HTTP-запросы истории продолжали ожидать единственный DB connection. Тест воспроизвёл это при занятом connection. Теперь QueryContext отменяет очередь и запрос, общий deadline — 10 секунд.
- CSV отправлялся непосредственно из открытых rows. Остановив получателя на первом Write, тест получил timeout другого DB-запроса. Теперь SQL закрывается после подготовки частного временного CSV, до отправки.
- Добавление маршрута удерживало App.mu во время ожидания SQL; эта же блокировка нужна fallback-странице. Убрано ожидание SQLite под App.mu, отдельный regression-тест проверяет доступность читателей при занятой БД.
- Backup удерживал stateMu во время сетевой отправки. Теперь блокировка освобождается после подготовки файла. Тест медленного получателя проверяет, что flushTraffic продолжает сохранять новые байты.
- Массовое удаление истёкшей истории заменено небольшими транзакциями с бюджетом времени. Политика 90 дней не сокращена, totals/платежи не удаляются.

Схема SQLite не менялась, переключение на другую СУБД не требуется для этих исправлений. WAL и один connection сохранены. [SQLite WAL](https://sqlite.org/wal.html) поддерживает конкурентные чтения/запись, но удержание единственного connection самим приложением всё равно создаёт очередь. Смена СУБД не исправила бы лимиты HAProxy и память Go.

## Проверки и границы результатов

`go test -race ./...`, `go vet ./...`, `python3 deploy/test-update.py` и полный Docker TLS-тест. Отдельные opt-in benchmarks:

```bash
go test ./cmd/panel -run '^$' -bench 'BenchmarkHistoryGrowth|BenchmarkRelayTCP' -benchtime=1s
python3 deploy/test-integration.py --seconds 300 --history-days 90
```

На Apple M2, локально, искусственная история 20 маршрутов: холодный запрос за 1 день около 15 ms, за 90 дней (2 592 000 строк samples) около 3.19 s. Это демонстрирует рост стоимости больших диапазонов, но не доказывает влияние на конкретный сервер с историей в несколько дней. Кэш на 30 секунд хранит лишь готовые графики (не более 64 ключей), ускоряя повторные запросы; холодный запрос остаётся ограничен 10 секундами.

Пятиминутный тест TLS в Linux Docker с четырьмя потоками после исправления лимитов и буферов: среднее 7.556 Gbit/s; в конце 18 Go goroutines, 0 активных route relay-соединений. Это синтетический локальный тест, не замер интернет-канала и не гарантия многосуточной стабильности. Сравнивать абсолютные значения между запусками с другой фоновой нагрузкой некорректно.

Отдельный финальный прогон: 120 секунд TLS параллельно опросу графиков, 90 дней синтетической истории для 3 маршрутов (по 388803 строки в каждой таблице, около 47 MB основной БД). Среднее 7.849 Gbit/s, ошибок сохранения не зарегистрировано, после нагрузки 18 goroutines и 0 route relay-соединений. Пара графиков вместе с `/system` занимала 0.83–1.21 s при пересчёте и 10–37 ms из кэша. Файл WAL около 47.5 MB после генерации истории оставался переиспользуемым: размер файла WAL сам по себе не равен объёму незафиксированных данных и не доказывает неисправность.

## Что нужно с работающего сервера

Разовый `deploy/diagnose.py` до перезагрузки: фактически запущенные image ID, CPU/RAM/OOM, текущие/max HAProxy-сессии, размеры БД/WAL, очередь/ошибки сохранения, swap/iowait и сводка TCP. Скрипт работает и со старой версией панели, не меняет настройки или данные и не печатает секреты. По результату можно отличить насыщение соединений от SQLite, сети, upstream или ресурсов хоста. Без этого нельзя обещать, что все причины конкретного инцидента устранены.
